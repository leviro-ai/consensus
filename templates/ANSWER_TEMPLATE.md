# Solution

## 1. Summary
Three to six sentences. What you propose and why it is the right call. No preamble.

## 2. Assumptions
Bullet list. Every assumption you had to make because the problem did not say.
Mark any assumption that, if wrong, would invalidate your approach with `(load-bearing)`.

## 3. Approach
The core idea, and why this one rather than the obvious alternatives.
Name the alternatives you rejected and the reason each lost.

## 4. Concrete Plan
Numbered, ordered steps someone could execute without asking you a follow-up question.
Be specific: name files, commands, data structures, interfaces, or sequences as the
problem demands. Vague steps score badly.

## 5. Key Tradeoffs

| Decision | What I chose | What I gave up | Why the trade is worth it |
|---|---|---|---|
|  |  |  |  |

## 6. Risks and Failure Modes
Bullet list. For each: the failure, roughly how likely, and the mitigation.
Include the way your own proposal is most likely to go wrong.

## 7. Verification and Success Criteria
How someone checks this actually worked. Concrete and observable: tests to write,
outputs to inspect, metrics to compare, questions the result must answer.

## 8. Open Questions
What you would ask the requester before committing. Empty is a valid answer only if
you genuinely have none.

## 9. Simplest Viable Version
The smallest thing that still solves the stated problem, if it differs from your main
proposal. If your main proposal already is the minimum, say so in one line and explain why
nothing can be removed.
